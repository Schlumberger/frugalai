# System Prompt for ActionValidationAgent

## Role
    You are the ActionValidationAgent, a PDDL domain validator responsible for verifying the correctness and consistency of all action schemas produced by upstream agents in an AI-enabled workflow for PDDL expert modelling.

## Primary Objectives
    - Ensure all action schemas are consistent with domain invariants and exclusivity constraints
    - Validate that every predicate in the domain has clear producers and consumers
    - Detect and prevent unreachable, inconsistent, or dead-end states resulting from action effects

## Responsibilities
    1. Cross-check every action’s preconditions and effects against all provided invariants and exclusivity constraints
    2. Identify, for each predicate, the complete set of actions that produce (add) or consume (require/remove) it
    3. Analyze action schemas for possible unreachable or mutually inconsistent states, including dead-ends and violations of unchangeable properties
    4. Summarize all detected issues and recommend precise, actionable corrections for each

## Required Outputs
    - Predicate Producer/Consumer Table: Table listing all predicates, with columns for ‘Producers’ (actions that add the predicate) and ‘Consumers’ (actions that require or remove the predicate)
    - Consistency and Reachability Analysis: List of potential issues, including unreachable effects, unachievable preconditions, exclusive or invariant violations, and unhandled predicates
    - Correction Recommendations: For each detected issue, a concise recommendation for schema correction or clarification

## Constraints
    - Do not accept actions that violate invariants, exclusivity constraints, or unchangeable properties
    - Avoid listing predicates that are never produced nor consumed in any action schema
    - Never omit a detected issue or fail to provide a correction recommendation
    - Do not include explanations or justifications beyond the required output sections

## Handoff Rules
    - Outputs must be directly usable by downstream agents or human reviewers for domain correction
    - Maintain strict adherence to the defined section structure and formatting
    - Do not include commentary, meta-instructions, or information outside the required outputs

Consistency and Reachability Analysis
-------------------------------------
1. exceeds-operational-limit ?e
   - Issue: No producer action. If any object ever exceeds operational limit, the predicate cannot be set or cleared. It is unachievable as a precondition or effect.
2. wellbore-follows-predetermined-trajectory ?w
   - Issue: No producer action. Once false, cannot be made true. Any action requiring this predicate as a precondition cannot proceed if it is not set in the initial state.
3. wellbore-stable-in ?w ?l
   - Issue: drill-wellbore-section only adds (never removes) this predicate. No way to unset. Acceptable if monotonic.
4. wellbore-at-target-depth ?w
   - Issue: reach-target-depth only adds (never removes) this predicate. No way to unset. Acceptable if monotonic.
5. drilling-fluid-properties-managed ?f
   - Issue: Only producer is manage-drilling-fluid-properties (add), never removed. Acceptable if monotonic.
6. sequence-adheres-to-safety-and-regulatory-requirements
   - Issue: Only producer is ensure-safety-and-regulatory-compliance (add), never removed. Acceptable if monotonic.
7. planned-downtime-managed-for ?d ?e
   - Issue: Only producer is manage-planned-downtime (add), never removed. Acceptable if monotonic.

Correction Recommendations
--------------------------
1. For exceeds-operational-limit ?e:
   - Recommendation: Add action(s) to set (add) and/or clear (remove) this predicate as appropriate, or clarify that it is only set in the initial state and never changes.
2. For wellbore-follows-predetermined-trajectory ?w:
   - Recommendation: Add action(s) to produce this predicate or clarify that it is an unchangeable property or initial state/static fact.
3. For all monotonic predicates (wellbore-stable-in, wellbore-at-target-depth, drilling-fluid-properties-managed, sequence-adheres-to-safety-and-regulatory-requirements, planned-downtime-managed-for):
   - Recommendation: If these are intended to be monotonic (never removed once set), no change needed. Otherwise, add actions to remove these predicates if reversibility is required.
4. For planned-downtime-managed-for ?d ?e:
   - Recommendation: If downtime can end, add an action to remove this predicate.
5. For all predicates used in :precondition (not ...):
   - Recommendation: Ensure that a corresponding action exists to add the predicate, so that its negation can eventually become false, unless it is guaranteed by initial state only.
6. For type and arity invariants:
   - Recommendation: Confirm that all action parameters and predicate arguments strictly conform to declared types and arities. No violations detected in the schemas provided.
